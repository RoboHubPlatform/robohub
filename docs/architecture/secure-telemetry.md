# Secure telemetry

One owner for telemetry, and every link between the parts that produce, carry and
use it authenticated, fresh and bounded in time. This page is the design, and all
of it is implemented; {ref}`architecture/security` is the shorter account of who
may do what, and {ref}`architecture/reading` follows one reading through it.

## The parts and who trusts whom

```
 board ──frames──▶ gateway ──outbox──▶ mesh ──/mesh/api──▶ aquarium, energy, ...
   K_dev, session     K_gw, RP of keeper   owner, RP of keeper     RP of keeper
                                  ▲               ▲                       ▲
                                  └───── short-lived tokens from keeper ──┘
```

- **keeper** is the only issuer. It holds the one ES256 (P-256) private key and
  publishes the public key. Nothing else reads its files or holds its key.
- **mesh** is the only owner of telemetry: it alone ingests from gateways, stores
  readings, names sources and actuators, and brokers commands. No other
  application opens its database, and no other application has a telemetry store.
- **gateway** carries frames between boards and mesh. It authenticates boards by
  their device key and mesh by keeper's tokens.
- **aquarium, energy** and any later application hold domain state only. They read
  sources and send actions through `/mesh/api`, with a token keeper issued.

## Users: one session per application

A browser signs in at keeper and comes back to an application with a one-use
ticket. The application then keeps **its own** session:

- the cookie is named for the application's audience (`rho_session_<aud>`), so
  two applications on one host do not overwrite each other;
- its value is a keeper-signed session token for that audience, valid for at most
  eight hours, verified with keeper's public key; there is no shared session file;
- the token's audience must be the application's own; a token for another
  application is refused.

## Services: short-lived tokens

A service that calls another (an application calling mesh, mesh calling a
gateway) holds a **client credential** keeper registered for it: an id and a secret,
stored by keeper as a hash and by the service in its workspace with mode 0600. It
exchanges the credential at keeper for a token:

```
POST /auth/service-token   client_id, client_secret, audience, scopes
→ { token, expires_in }    ES256, aud = the callee, scp = granted scopes, ttl ≤ 10 min
```

The caller caches the token and renews it at 80 % of its lifetime. A callee
verifies it offline with keeper's public key; nothing is looked up per request.

Every relying party, generated by Rho's auth middleware:

- removes `X-Rho-Subject`, `X-Rho-Scopes` and `X-Rho-Aud` from every incoming
  request before anything else, exempt path or not, and sets them only from a
  token it verified;
- requires the token's audience to be its own;
- grants a route group only to the scopes it declares (`mesh:<project>`,
  `gateway:<id>:read`, `gateway:<id>:command`).

## Gateway and mesh

The gateway is a relying party of keeper with the audience `gateway`. It knows its
own id (`GATEWAY_ID`, the mesh's name), and the scopes name it:
`gateway:<id>:read` for telemetry, the outbox and diagnostics, `gateway:<id>:command`
for switching and commands; `gateway:<id>:*`, `gateway:*` and `*` hold both. There
is no static token. Mesh may be issued `gateway:*`, but asks each gateway's token for
`gateway:<id>:*`, so a token taken from the network opens that gateway and no other.
A gateway reached over a network serves HTTPS when the mesh names its certificate
and key (`gateway_tls_cert`, `gateway_tls_key`).

The outbox keeps a **cursor per consumer** (the token's subject) and retains
records by age and size, rather than deleting what the first consumer
acknowledged. In practice mesh is the one consumer, and this makes a second one
(a backup, a debugger) harmless.

## Boards and gateways: authenticated frames

### Keys

- Every gateway has a 256-bit gateway key `K_gw`. Mesh creates it when it plans
  the gateway and installs it with the gateway (the same deployment that already
  starts it over SSH or ADB), in a file readable only by the gateway's user.
- Every device has a 64-bit device id `uid`: the chip's unique id when the part
  has one, otherwise minted by mesh when the node is planned and built into its
  firmware.
- The device key is derived, not stored or sent: `K_dev = HMAC-SHA256(K_gw,
  "rh-dev1" ‖ uid)[0:16]`. Mesh derives it to build the firmware; the gateway
  derives it when the device says hello. No key crosses a network.

### Session handshake

```
board   → HELLO   { uid, nonce_b(8), firmware, platform, capabilities }      tag with K_dev
gateway → SESSION { session_id(2), nonce_g(8), lifetime_s(2), time_ms(4) }   tag with K_dev
both    K_up   = HMAC-SHA256(K_dev, "rh-up1"   ‖ nonce_b ‖ nonce_g)[0:16]
        K_down = HMAC-SHA256(K_dev, "rh-down1" ‖ nonce_b ‖ nonce_g)[0:16]
```

A session lasts `lifetime_s` (one hour by default) or until a counter would wrap,
whichever is first, and then the board says hello again. A gateway restart loses
its sessions, and boards re-handshake on the first rejected frame.

### Secured frame

The framing stays what it is (COBS, the six-byte header, the check), so a parser
finds boundaries as before. A secured frame adds a trailer inside the payload area:

```
header(6) ‖ session_id(2) ‖ counter(4) ‖ payload ‖ tag(8) ‖ check(2)
tag = HMAC-SHA256(K_dir, header ‖ session_id ‖ counter ‖ payload)[0:8]
```

The receiver drops a frame whose session is unknown or expired, whose counter is
not greater than the last one accepted in that direction, or whose tag does not
match. Truncating HMAC-SHA256 to 64 bits is standard for a low-rate link; at the
rates a sensor sends, forging a tag by guessing is not a practical attack within
a session's lifetime.

This provides authenticity, integrity, replay protection and freshness. It does
not encrypt: readings and commands are not secret, but they must not be forged or
replayed. Encryption (an AEAD with the same keys and counters) can be added
without changing the handshake.

A relay link (gateway to gateway) uses the same frames. The relay is a device of
its parent, with `uid` its gateway id, and its key is derived from the parent's
`K_gw`.

## Live UI: HTMX and SSE

Applications stay small by staying server-rendered, as {ref}`build/reactive-ui`
lays down: a page opens one SSE connection, the server sends HTML fragments, and
HTMX swaps them in. Nothing in a browser polls, and nothing in a browser talks to
mesh or a gateway.

```
mesh ──SSE (service token, per project)──▶ app server ──SSE fragments──▶ browser (HTMX)
     ◀──POST action (service token)───────            ◀──hx-post───────
```

- **Mesh streams per project.** `/mesh/api/projects/{project}/telemetry/stream`
  serves that project's events only, with a snapshot of current values first, so
  a reconnect starts from the present.
- **An application relays, it does not store.** Its server holds one
  subscription to mesh's feed for its project with its service token, renders the events
  that concern its widgets as fragments, and serves them on its own page stream.
  The browser never sees a mesh URL or a token.
- **Actions are forms.** A button or switch is an `hx-post` to the application,
  which checks the user's session and forwards the action to mesh with its own
  service token. Mesh brokers it to the gateway, and the new state comes back on
  the stream. No state is guessed in the page.

The relay is the runtime's `rho_sse_follow`: it follows a remote SSE stream into a
local file with a service token, for as long as the application runs, and the
application serves its own page stream from files (`sse_events`). When the
installation runs the MQTT broker, Mesh also relays each project's feed to the topic
`mesh/<project>/telemetry`, and an application's gateway provider can follow that
instead (`transport: auto | bus | http` in its binding).

## Source identity

A source or actuator is named by `(gateway_id, uid, signal)`, which survives a
reordered plan, a renamed folder and a renumbered node. Mesh keeps the mutable
facts (area, node, label, the firmware's `module.id`) in a `telemetry_source`
table and keys readings by the source; the numeric area and node remain only as
routing on the wire.

## Where it is implemented

| Part of the design | Code |
|---|---|
| Header stripping, per-application sessions, audience and scope checks | Rho's auth middleware, generated into every relying party |
| Service tokens and the client registry | the keeper (`/auth/service-token`) and the `rho auth` component |
| One telemetry owner, streamed per project | Mesh, with its store as the `mesh-telemetry` port |
| Applications reading Mesh with service tokens and relaying its feed | `robohub-provider-mesh` and the widgets module |
| The gateway as a relying party; the outbox with a cursor per consumer | `robohub-gateway` (`security.rho`, `outbox.rho`) |
| Authenticated frames | `robohub-transport` (`secure.h`), the gateway (`secure.rho`), Mesh's firmware generation, relay links |
| Source identity | Mesh's `telemetry_source` table; readings keyed by source |
